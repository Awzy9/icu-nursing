# Critical care nursing — P1 Batch 15: website/mobile draft-publication safeguards
**Date:** 2026-11-23  
**PR:** [Awzy9/icu-nursing #113](https://github.com/Awzy9/icu-nursing/pull/113)  
**Status:** DRAFT, unmerged, not clinically approved. No production environment settings changed.

## Audited exposure
- Existing `CONTENT_EDITION=working` made AI-authored draft bodies, scenario options and question answers accessible from site pages and public `/api/content/*` endpoints. A visible `WorkingNotice` explained the material is not clinically approved, but the actual runtime gate did **not** enforce individual clinical review.
- The website and mobile read the same working catalog; lab datasets (ECG, blood/transfusion, CRRT, etc.) were also served via content APIs. Publication isolation must cover both content routes and lab files.
- All 40 core draft topics, 20 clinical-scenario drafts, medications, skills, equipment and practice remain *unreviewed* and should not silently graduate to an approved release. UI tests and source/markdown validation do **not** substitute for clinical or rights review.

## Implemented fail-closed design, on the PR branch only
1. `content/publication-approvals.json`: explicit empty release register. No named human reviewer, clinical approval, source-rights permission, or publisher approval has been invented.
2. `src/lib/working/publication-policy.ts`: per-entry eligibility requires a matching **full SHA-256 hash** of the exact generated working entry and its **source draft audit hash** (including metadata/evidence revisions), `clinically_reviewed: true` in the staff draft index, no validation issues, registered evidence sources, named clinical reviewer, independent publisher, rights-review reference, commercial source-use clearance and dated sign-offs. **Topic-derived QB entries** also require the underlying parent topic to be reviewed, plus a separate approval for the question entry. Stale, duplicate, missing and incompatible records fail closed.
3. `src/lib/working/publication-gate.ts`: checks the **entire** public release set and the exact byte hashes of all twelve supporting `content/working-*.json` educational lab/visual datasets (including CRRT and transfusion); missing or stale lab approvals block the release. This prevents a text-only approval from implicitly approving a risk-bearing lab.
4. `src/lib/working/index.ts`: working edition is available as a clearly labelled preview only when `NEXT_PUBLIC_APP_ENV` is explicitly `staging` or `development` **and** Vercel does not report `VERCEL_ENV=production`. A production-hosted working edition is unavailable unless the complete review/rights gate passes, including when `NEXT_PUBLIC_APP_ENV` is absent or misleading. Shared `workingEditionEnabled()` gates all existing website and native content API routes (catalog, exam, revision, specialized labs, case visuals, CRRT, paths).
5. `scripts/build-working-content.ts`: refuses a working-edition production build with a detailed blocked count until every served catalog item and lab dataset has the necessary sign-off. The normal CI/demo build with `CONTENT_EDITION` unset is unchanged.
6. `playwright.working.config.ts`: explicitly sets the **staging** application environment for the isolated, synthetic working-edition UI tests instead of relying on a missing production/staging distinction.
7. `tests/unit/p1-publication-gate-batch-15.test.ts`: verifies zero release approvals, all unreviewed catalog entries and lab datasets blocked, production website/mobile content guard, source-hash invalidation, independent reviewer/rights checks, duplicate rejection and both build- and runtime-control references.

## Important limits and reviewer instructions
- **No approvals entered**, no removal of draft banners, no source rights represented as cleared, no merge or production deployment. Existing preview behavior is intentionally preserved on *explicitly configured* development/staging environments. Staging previews **can still be publicly accessible** if their hosting/network access is public; their disclaimer is not access control. Configure preview access protection (identity/hosting) separately if staff-only access is required.
- The release registry is part of the GitHub repository, so write access remains privileged; names and clearance references **must be verified by a human publisher**, not generated by AI. Hash matching is an integrity guard, not proof of a medical qualification or copyright licence.
- If someone attempts to deploy `CONTENT_EDITION=working` into Vercel production before review, the build will intentionally fail (and runtime gate will deny access). **Do not merge this PR expecting it to publish the existing working edition.** Product and clinical teams must choose a staged review strategy before production adoption.
- `CONTENT_EDITION` unset uses the application's separate non-working content paths, which have their own review/publishing controls and are **not certified by this change**. This gate does not prove *all* web, static, CDN or legacy routes are free of unapproved content; security and release QA are still required.
- The twelve dataset approvals are independent of catalog approvals. Even if every lesson has been reviewed, lab data, interactive cases and visual resources require their own content- and licence-review records.
- The draft index and generated history are not altered, and the original curriculum counts are unchanged.
- **Before clinical publication:** named qualified ICU nursing and relevant specialty reviewers, pharmacist/transfusion/nephrology/RT as appropriate, independent publisher, commercial rights confirmation, full CI and endpoint verification, then deliberate release config changes.
