# Equipment and monitoring education (Phase 9)

## Scope
Eight initial device categories, in this order: bedside monitors and alarms; ventilator controls and waveforms; arterial pressure monitoring systems; infusion pumps; defibrillators; CRRT systems; enteral feeding pumps; pressure-relieving equipment (`EQUIPMENT_CATEGORIES` in `src/lib/equipment/types.ts`).

## Two separate things
1. **The learner-facing section** (`/equipment`, `/equipment/[code]`). It serves only **synthetic, nonclinical fixtures** (`src/lib/equipment/synthetic-equipment.json`, codes `SYN-EQ-001..008`, fictional devices such as a harbour display panel or a garden drip pump, English and Arabic). The schema requires `synthetic: true` and the `SYN-EQ-` code, so a real draft cannot be served by mistake (unit test). Disabled when sample content is switched off (same mode switch as the skills library).
2. **The real equipment drafts** (`content/drafts/equipment/EQ-01..EQ-08`). Device-neutral specifications generated by `build_equipment.py` from the already-traced safety, monitoring and escalation statements of the matching skill drafts (SK-18, SK-07, SK-01, SK-22, SK-19, SK-17, SK-10, SK-14). Parameter explanations are listed with `explanation: null, support: needs_source` because no source read explains them; none were invented. Drafts that rely on manufacturer documents (Hamilton, Draeger, an AHS pathway for one CRRT machine family) record the device and version in `manufacturer_documents`, are marked not device-neutral, and say the statements apply to that device only. Validator: `src/lib/equipment-draft-validator.ts`, `npm run validate:equipment`, `tests/unit/equipment.test.ts`. These drafts are not imported or shown anywhere.

## Features
* Overview page grouped by category with a "bookmarked only" filter and a progress summary.
* Detail page: an **original generic schematic** (loop, signal trace or flow path drawn from simple shapes; no manufacturer screens, icons, alarm tables or manual content), a text alternative in the SVG `<title>/<desc>` and a visible caption, a keyboard-operable parts list (buttons with `aria-pressed`, live-region explanation), "what is measured or shown", safety concepts, and escalation.
* Progress (parts viewed) and bookmarks are kept in `localStorage` on the device only, with every access guarded; they are **not** synced to an account. Account-level persistence would need a migration, RLS and RPC tests and is left for a later phase.
* English and Arabic: logical (start/end) layout classes, SVG positions mirrored for RTL, English fallback marked `lang="en" dir="ltr"`.
* Tests: `tests/e2e/equipment.spec.ts` (axe at three viewports, Arabic RTL, keyboard operation, persistence, 404s) and `tests/unit/equipment.test.ts`.

## Not done
No database tables, no learner data on the server, no link into the skills or case engines yet (the draft specification names the related skill; a later phase can connect the section to skill sessions or case observations). No real equipment content is published.
